# 날짜 전체 차단 기능 — 운영 배포 순서

> 안전 안내: 현재 운영 중인 `main` 및 Supabase는 이 작업 브랜치만 생성한 것으로 변경되지 않습니다.
> **반드시 서버(SQL → Edge Function)를 먼저 적용하고 GitHub Pages(main)를 마지막에 반영하세요.**

## 기능
- 관리자 화면 → 시간 차단 → 차단 날짜 지정 → 차단 시각 목록의 **선택한 날짜 전체 차단 (32개 시간)**.
- 09:00~17:45, 15분 간격, 12:00~12:45 점심 제외한 32개 슬롯이 한 번에 차단됩니다.
- 통합(전공·취업·일반)과 창업은 독립적으로 차단됩니다.
- 해당 그룹/날짜에 **활성 예약이 한 건이라도 있으면 전체 차단이 실패**합니다. 이전 예약은 절대 변경·취소되지 않고 새로운 차단도 0건 적용됩니다.
- 기존 개별 차단이 있다면 보존하며 32개까지 채웁니다. 재시도 시 중복되지 않습니다.
- 해제는 기존 팝업의 개별 슬롯 × 버튼으로 계속 가능합니다. 이번 기능에서는 하루 일괄 해제는 추가하지 않았습니다.

## 배포 (Supabase 실운영 계정 필요)
1. Supabase Dashboard → SQL Editor → 새 쿼리 생성.
2. 이 브랜치의 `supabase/migrations/202610190001_block_day.sql` 전체 코드를 복사해 **한 번 실행**합니다. 새 함수만 생성하며 기존 테이블/예약/차단 데이터를 변경하지 않습니다.
3. Supabase Dashboard → Edge Functions → `monitoring-api` → 편집.
4. 이 브랜치의 `supabase/functions/monitoring-api/index.ts` 전체로 교체 후 **Deploy**합니다.
5. **기존 관리자 사번 2개와 세션 비밀키는 변경하지 마세요.** JWT verify 설정은 기존처럼 꺼 둡니다.
6. 위 2개 서버 변경이 성공한 후 이 작업 브랜치의 내용을 GitHub `main`으로 병합하여 GitHub Pages를 갱신합니다.
7. 일반 크롬에서 `Ctrl + Shift + R`로 새로고침합니다.

## 검증
- 실제 예약 없는 날짜를 선택해서 **선택한 날짜 전체 차단** 실행 → 차단된 시각 총 32개 확인.
- 같은 날짜 전체 차단 재시도 → 32개 유지(중복 없음).
- 전공 담당자 날짜 전체 차단이 창업 담당자 예약 목록에 영향 없는지 확인.
- 기존 예약이 있는 날짜 선택 → 오류만 표시되고 기존 예약/차단은 유지되는지 확인.
- 기존 개별 차단/차단 해제 동작 유지 확인.
- 테스트 종료 후 임시 차단을 개별 해제해서 원래 운영 상태로 복구.
- 실제 운영 서버에서 전체 차단 테스트는 반드시 동아리가 사용하지 않는 시간대/날짜에서 조심스럽게 진행하세요.
